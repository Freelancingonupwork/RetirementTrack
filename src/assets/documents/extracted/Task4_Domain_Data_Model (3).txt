RETIREMENTTRACK
Domain & Data Model
# 1. Purpose and Scope
Define the initial RetirementTrack domain model, data ownership boundaries and key relationships required to support the first credible MVP.
Task 4 outcome: a tenant-aware business model that clearly identifies the core entities, ownership, relationships, lifecycle, authorization boundaries and unresolved business decisions before detailed technical architecture is finalized.
# 2. High-Level Domain Structure
Platform → Firm/Tenant → Tenant Memberships & Configuration → Advisors / Clients → Assignments → Assessments / Planning Updates / Opportunities / Content / Reminders / Communications → Updated Client State / Advisor Exceptions
The primary security and ownership boundary is the Firm/Tenant. Platform-level data may be shared across tenants only where explicitly designed as common platform content or configuration. Client-specific records remain tenant-scoped even when they originate from common definitions such as an assessment template or educational resource.

# 4. User and Role Model
Identity, tenant membership, role and client assignment should be modeled separately. This prevents the application from treating a user role as proof of tenant or client access.
Entity
Recommended Responsibility
User
Platform identity record: name, email/login identity, user status and authentication linkage.
TenantUserMembership
Links a User to a FirmTenant and records membership status/effective dates.
UserRoleAssignment
Assigns one or more tenant-scoped roles to a membership.
PlatformRoleAssignment
Stores platform-level operational roles separately from firm membership.
ClientProfile
Holds client-specific profile/context separate from the authentication identity.
AdvisorProfile
Optional advisor-specific professional/contact attributes used by RetirementTrack.

# 5. Advisor–Client Relationship
Advisor access should be based on an explicit tenant-scoped relationship, not merely on the Advisor role. The assignment record should support authorization, ownership, reassignment and history.
Area
Recommended MVP Model
Relationship entity
AdvisorClientAssignment links Advisor membership/profile to a Client within the same FirmTenant.
Primary advisor
Allow zero or one active PrimaryAdvisor assignment per client; use as default advisor identity and follow-up owner where applicable.
Secondary advisors
Keep the schema capable of additional assignments, but enable only if business need is confirmed.
Reassignment
End the prior assignment with EffectiveTo/Ended status and create a new assignment; do not overwrite history.
Historical assignments
Retain prior assignments for audit, communication context and historical workflow attribution.
Visibility
Advisor client access requires same tenant + active authorized assignment (or another explicitly approved permission path).
Firm Admin visibility
Firm Admin can manage relationships but should not automatically receive unrestricted sensitive client detail.
Open work transfer
Define whether reassignment transfers open exceptions/follow-up items to the new advisor or preserves prior ownership.

## 6.1 Household Model
Household support is now part of the recommended MVP domain. The model should link spouses/partners without replacing each person’s individual identity, login, assessment history or permissions.
Entity / Concept
Recommended MVP Model
Household
Tenant-scoped relationship container for a spouse/partner household. Hold shared household context only where the business meaning is genuinely shared.
HouseholdMember
Links an individual ClientProfile to a Household with relationship type, effective dates and an optional primary/contact indicator.
Individual identity
Each spouse/partner remains a separate User/ClientProfile with independent authentication, consent, assessment results and activity history.
Shared advisor relationship
Household members may share an advisor, but advisor authorization should still resolve to explicit client assignments unless a future household-wide rule is deliberately introduced.
Shared data boundary
Use household-level fields only for data naturally defined at household level, such as household income/net worth when required for benchmarking; avoid duplicating personal data.
MVP boundary
Support spouse/partner linking and shared context. Defer complex household hierarchies, trusts/entities and advanced shared-workflow behavior.
# 7. Assessments and Results
Entity
Purpose / First-Build Boundary
AssessmentDefinition
Defines an approved assessment type; use a small fixed first-build inventory. Current working examples include a fuller client questionnaire and a condensed Investment & Risk Assessment.
AssessmentVersion
Preserves question/scoring changes over time; completed assignments remain tied to their version.
AssessmentQuestion / Option
Structured questions and answer choices supported by the selected assessment.
AssessmentAssignment
Links an assessment/version to a client, assigning advisor, due state and status.

Creates advisor attention when an approved result condition requires review; may map to the common exception/follow-up model.

# 8. Planning Update Model
Planning Update should be modeled as a recurring first-build workflow rather than a generic form. The model must support cadence, due state, client completion, comparison with prior state, defined change detection, advisor follow-up and updated client history.
Entity / Concept
Recommended First-Build Model
PlanningUpdateDefinition
Fixed initial form/question set and version.
PlanningUpdateInstance
Client-specific scheduled/due occurrence with status, due date and completion date.
PlanningUpdateResponse
Client responses for the instance.
Prior-state comparison
Links relevant current values to prior completed state for defined change detection.
PlanningUpdateDetectedChange
Stores each defined change with change type, prior/current value or references, severity/reason, advisor-attention flag and source Planning Update instance.
Follow-up link
Only meaningful changes or explicit review conditions create an AdvisorException/FollowUp item. A completed Planning Update does not automatically create advisor work.
Client state update
Completion/change outcomes update history and may alter future priorities, content or reminders.

Concept
Recommended Boundary

# 11. Benchmarking Model
Benchmarking should be modeled as a small, credible first-build capability using curated reference data where the measure, source, cohort method, calculation and client-facing explanation are validated. Current working examples are median household income, median household net worth and median retirement savings by age; these are examples for evaluation, not automatically final production measures.
Entity
Purpose / Boundary
BenchmarkDefinition
Defines the benchmark measure, unit, comparison method and client-facing explanation/caveat.
BenchmarkDataSource
Records source provenance, maintainer, source type, publication/reference details and validation status.
BenchmarkDataVersion
Represents a versioned/effective snapshot of source data and methodology used for deterministic calculations.
BenchmarkReferenceValue
Stores curated reference values by benchmark definition, age/age band or other validated cohort dimension, percentile where applicable, effective year/version and source.
BenchmarkCohort
Defines explainable cohort logic such as age or retirement stage where a separate cohort abstraction is useful.
ClientBenchmarkResult
Stores the client comparison result or reproducible calculation reference, including client input snapshot/reference, benchmark version and generated date.
BenchmarkVisibility
Firm enablement and advisor/client visibility according to permissions and MVP configuration.
Fallback state
If required client inputs or validated benchmark data are unavailable, represent unavailable/not-calculable rather than fabricate a result.

## 15.1 Working Business Guidance Confirmed During Discovery
Area
Working Direction
Target firm model
Design for established independent wealth-management and CPA/advisory firms with multiple professionals and several hundred to a few thousand client households.
Households
Support household relationships, particularly spouses/partners, in the MVP domain model.
Assessments
Use a small fixed initial set. Current examples include a fuller client questionnaire and a condensed Investment & Risk Assessment; no generalized form builder.
Planning Update
Keep as a core recurring workflow. Completion updates client state; only meaningful changes or explicit review conditions create advisor attention.
Personalization
Favor a small number of clearly relevant priorities driven by life stage, activity, milestones, assessment/Planning Update state and firm/advisor context.
Advisor control
Provide practical review/approval/suppress/dismiss controls where needed, but avoid extensive configurable workflow or override capabilities.
White labeling
MVP baseline is firm logo, selected brand colors and advisor identity. Custom domains/sender identities remain conditional.
Reporting
No broad reporting engine. Keep useful client outputs and operational information advisors need to identify clients requiring attention.
Benchmarking
Evaluate a very small number of simple, credible benchmarks. Current examples are median household income, median household net worth and median retirement savings by age, subject to source/methodology validation.

# 17. Final Recommended Domain Boundary
Recommended domain core: Firm/Tenant + membership/roles + clients/advisors + explicit advisor-client assignments + assessment/result history + recurring Planning Updates + explainable priority/opportunity state + relevant content + reminders/communications + advisor exceptions + tenant configuration + bounded benchmarking + audit/history.
Include as First-Build Domain
Keep Simple / Defer
FirmTenant, tenant configuration, user membership, built-in roles, Household/HouseholdMember and advisor-client assignments
No enterprise org hierarchy, complex household structures, brand tree or custom permission designer.
Fixed assessment definitions/versions, assignments, responses and results
No generalized assessment/form builder.
Fixed Planning Update workflow with prior-state comparison, explicit detected changes and follow-up linkage
No generalized workflow engine.
Rules-based priorities/opportunities, client state and content relevance
No AI/ML recommendation engine or firm-authored rule builder.
Reminder/communication records, approval state and history
No marketing automation/campaign platform.
Benchmark definition/source/version/reference-value entities sufficient for a small validated age/cohort comparison
No sophisticated cohort analytics, dynamic peer benchmarking or broad readiness scoring.
Audit/history and tenant-scoped authorization metadata
No unnecessary duplication of every business event into a large event-sourcing platform.
