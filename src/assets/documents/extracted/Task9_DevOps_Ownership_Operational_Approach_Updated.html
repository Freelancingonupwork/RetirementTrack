RETIREMENTTRACK

Task 9 – DevOps, Ownership & Operational Approach

Discovery deliverable defining the operational foundation for source control, production ownership, environment separation, CI/CD, infrastructure as code, access control, monitoring, backup/recovery, incident handling, third-party account governance, documentation, and developer/vendor transition.

1. Purpose & Operating Principles

Task 9 converts the confirmed technical architecture into an operating model that keeps RetirementTrack portable, supportable and secure without introducing enterprise process overhead that is unnecessary for the MVP.

PrincipleRecommended Direction
RetirementTrack ownershipProduction-critical accounts, infrastructure, repositories and recovery controls are owned or controlled by RetirementTrack, not an individual developer or development firm.
Replaceable delivery resourcesDevelopers/vendors receive named, least-privilege access. A change in development resources must not prevent RetirementTrack from operating, deploying or recovering the platform.
Reproducible environmentsInfrastructure and deployment configuration are source-controlled and repeatable through Bicep and CI/CD.
Controlled production accessProduction access is named, MFA-protected, auditable and limited to operational need.
Operational simplicityUse Azure-managed services, Clerk Pro and Temporal Cloud rather than self-hosting infrastructure that does not create product differentiation.
RecoverabilityBackups, restore procedures, account recovery paths and runbooks are documented and periodically tested.

3. Source Control & Repository Governance

AreaRecommended Practice
Repository ownershipClient-controlled Git organization and repositories; development firms are collaborators, not owners.
BranchingProtected main branch; short-lived feature/fix branches; pull request required for production-bound changes.
ReviewAt least one appropriate review for material production changes; architecture/security-sensitive changes receive lead review.
Quality gatesBuild, automated tests and applicable dependency/security checks must pass before merge/deployment.
SecretsNo production secrets, private keys or credentials in Git history. Use Key Vault and protected deployment identities.
TraceabilityPreserve pull requests, commit history, release tags/build versions and deployment records.
Recovery administrationAt least designated RetirementTrack account owners/recovery admins should be able to regain repository access independent of a vendor.

4. Environment Strategy

EnvironmentPurposeOperational Boundary

7. Database Migration & Release Safety

ControlRecommended Practice
Migration ownershipEF Core migrations are source-controlled and reviewed with the application change that requires them.
CompatibilityPrefer additive/forward-compatible migrations so old and new application versions can coexist during staged deployment where practical.
Risky changesTake/confirm an appropriate recovery checkpoint before high-risk schema/data changes and test migration behavior outside production.
ExecutionApply migrations through a controlled deployment step or explicitly authorized migration job, not developer workstation scripts against production.
Failure handlingDefine whether a failed release rolls application code back or rolls forward with a corrective migration; destructive down-migrations should not be assumed safe.
AuditRetain migration/version and deployment history for operational diagnosis.

12. Independent Pre-Production Security & Architecture Validation

Before production launch, RetirementTrack should complete a focused independent review of the implemented security and operational controls. The reviewer should be qualified and independent from the developer or team responsible for implementing those controls. The objective is to verify that the actual production environment matches the approved architecture and Task 9 requirements, without turning the MVP into a burdensome enterprise audit or formal compliance certification.

Review areaWhat should be independently validated
Tenant isolationVerify that one firm/client cannot access another firm’s identifiable data across APIs, database access paths and background workflows.
Identity & accessReview Clerk integration, application authorization, RBAC, MFA, advisor/client relationships, privileged access and least-privilege assignments.
Azure & environment configurationConfirm production resources, environment separation and production access follow the approved architecture.
Secrets & credentialsValidate Key Vault, Managed Identity where supported, credential storage/rotation, pipeline secrets and absence of exposed production secrets.
Production-data controlsConfirm production client data is not routinely copied to lower environments or developer devices and that support/export access is controlled and auditable.
Logging, monitoring & auditConfirm sensitive payloads are excluded from broad logs and that monitoring, alerts, audit evidence and operational visibility work as intended.
Backup & recoveryReview Azure SQL/Blob/Key Vault recovery configuration and evidence of restore testing against the approved recovery approach.
Deployment controlsReview CI/CD approvals, migration controls, deployment identities, rollback/roll-forward procedures and production change traceability.
Findings & closureDocument findings by severity. Material/high-risk findings should be remediated or formally accepted by RetirementTrack before production launch, with revalidation where appropriate.

This independent validation should be included as a pre-production implementation activity and budget item. It is intended as a practical second set of eyes on the implemented controls. Broader penetration testing, compliance certification or formal audit can be added later if client, insurer, regulatory or commercial requirements justify it.

14. Production Data Restrictions

RuleOperational Requirement
Lower environmentsDo not copy production client data into Dev/QA/Staging by default. Use synthetic or sanitized datasets.
Developer devicesDo not download production databases, client files or bulk exports to developer machines for routine troubleshooting.
Support accessUse authorized, least-privilege access and prefer metadata/status views over sensitive payload inspection.
ExportsGenerate firm/client exports only through approved, auditable paths and according to confirmed portability/privacy policy.
Database accessRestrict direct production SQL access; use application/admin tooling where feasible and audit exceptional access.
LogsDo not use logs as a secondary store for sensitive client information.

15. Incident & Support Approach

StageRecommended Practice
DetectMonitoring/alerts, provider notifications or user reports identify an operational issue.
TriageEstablish severity, affected tenants/users, security/privacy implications and immediate owner.
ContainLimit impact: disable failing workflow/integration, roll back deployment, revoke credential or isolate affected component as appropriate.
RecoverRestore service/data using documented release, backup or provider recovery procedures.
CommunicateUse agreed escalation and client/firm communication responsibilities; avoid speculative or premature incident statements.
ReviewFor material incidents, record timeline, cause, corrective actions and follow-up ownership.
EvidencePreserve relevant deployment, audit, application and provider evidence consistent with privacy/retention policy.

Exact operational support hours, response expectations, escalation contacts and any service-level commitments remain business confirmations rather than assumptions in this Discovery document.

18. Developer / Vendor Onboarding & Offboarding

PhaseRequired Actions
OnboardingCreate named identity; enforce MFA; grant only required repo/Azure/provider roles; document access owner and purpose; provide approved development/runbook documentation.
During engagementAvoid shared credentials; use approved secrets/configuration paths; request temporary elevation only when necessary; keep work and deployment history in RetirementTrack-controlled systems.
Role changeReview and reduce access when responsibilities change.
OffboardingRemove repository, Azure, Clerk, Temporal, provider, VPN/remote and other production access promptly; revoke tokens/keys; rotate shared/non-user credentials if exposure is possible.
HandoffTransfer open work, deployment knowledge, runbooks and unresolved operational issues before engagement ends where practical.
VerificationConfirm RetirementTrack retains billing, account-owner and recovery access and that no vendor-only dependency remains.

21. Final Recommended Operational Boundary

Recommended first-build operational boundaryEstablish a professional but lightweight operating foundation: RetirementTrack owns the critical accounts and recovery paths; developers/vendors remain replaceable; environments and deployments are reproducible; production access is controlled and auditable; secrets are centrally managed; monitoring and recovery are documented; restore/deployment procedures are tested; and the implemented security controls receive an independent pre-production review. Avoid enterprise bureaucracy that does not improve MVP reliability, security or portability.
Include for MVP / Production ReadinessKeep Simple / Mature with Scale
RetirementTrack-controlled accounts, billing and recoveryNo vendor-owned production dependencies.
Dev/Staging/Production separationNo unnecessary duplicate enterprise platform stacks.
Bicep + CI/CD + controlled release approvalsNo heavyweight release-management suite required.
Key Vault, Managed Identity, RBAC and MFANo broad standing production administrator access.
App Insights/Azure Monitor/OpenTelemetry and actionable alertsNo exhaustive enterprise SIEM program unless risk/compliance requires it.
Azure-managed backup/PITR plus restore testingNo custom backup platform where managed capabilities meet confirmed RPO/RTO.
Documented incident, recovery and vendor-transition runbooksNo process bureaucracy beyond what supports reliable operations.
Temporal Cloud and Clerk Pro under RetirementTrack ownershipNo self-hosted Temporal or custom identity infrastructure for MVP.
Independent pre-production security/architecture reviewNo heavy enterprise audit or formal certification unless later required.
