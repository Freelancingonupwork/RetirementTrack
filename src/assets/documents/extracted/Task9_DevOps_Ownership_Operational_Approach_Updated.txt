RETIREMENTTRACK
Task 9 – DevOps, Ownership & Operational Approach
Discovery deliverable defining the operational foundation for source control, production ownership, environment separation, CI/CD, infrastructure as code, access control, monitoring, backup/recovery, incident handling, third-party account governance, documentation, and developer/vendor transition.
# 1. Purpose & Operating Principles
Task 9 converts the confirmed technical architecture into an operating model that keeps RetirementTrack portable, supportable and secure without introducing enterprise process overhead that is unnecessary for the MVP.
Principle
Recommended Direction
RetirementTrack ownership
Production-critical accounts, infrastructure, repositories and recovery controls are owned or controlled by RetirementTrack, not an individual developer or development firm.
Replaceable delivery resources
Developers/vendors receive named, least-privilege access. A change in development resources must not prevent RetirementTrack from operating, deploying or recovering the platform.
Reproducible environments
Infrastructure and deployment configuration are source-controlled and repeatable through Bicep and CI/CD.
Controlled production access
Production access is named, MFA-protected, auditable and limited to operational need.
Operational simplicity
Use Azure-managed services, Clerk Pro and Temporal Cloud rather than self-hosting infrastructure that does not create product differentiation.
Recoverability
Backups, restore procedures, account recovery paths and runbooks are documented and periodically tested.

# 3. Source Control & Repository Governance
Area
Recommended Practice
Repository ownership
Client-controlled Git organization and repositories; development firms are collaborators, not owners.
Branching
Protected main branch; short-lived feature/fix branches; pull request required for production-bound changes.
Review
At least one appropriate review for material production changes; architecture/security-sensitive changes receive lead review.
Quality gates
Build, automated tests and applicable dependency/security checks must pass before merge/deployment.
Secrets
No production secrets, private keys or credentials in Git history. Use Key Vault and protected deployment identities.
Traceability
Preserve pull requests, commit history, release tags/build versions and deployment records.
Recovery administration
At least designated RetirementTrack account owners/recovery admins should be able to regain repository access independent of a vendor.

# 6. CI/CD & Release Flow
Recommended release flowPull Request → Build/Test/Scan → Versioned Artifact → Deploy to Staging/UAT → Health/Smoke Validation → Authorized Production Approval → Production Slot Deployment → Validate → Slot Swap → Monitor / Roll Back if required.
Component
CI/CD Approach
React frontend
Install/build, lint/test as defined, produce versioned static artifact, deploy through controlled pipeline.
ASP.NET Core API
Restore/build/test, dependency/security checks, package once and promote the same release artifact.
.NET Temporal Worker
Build/test/package with the application release; deploy Azure-hosted Worker separately from API while maintaining compatible contracts/workflows.
Bicep
Validate infrastructure templates and deploy reviewed environment changes through pipeline.
Azure SQL
Apply reviewed EF Core migrations through controlled release sequencing; no ad hoc production schema edits.
Production
Use App Service deployment slots where applicable, health checks and explicit production approval. Keep a rollback/roll-forward path.
# 7. Database Migration & Release Safety
Control
Recommended Practice
Migration ownership
EF Core migrations are source-controlled and reviewed with the application change that requires them.
Compatibility
Prefer additive/forward-compatible migrations so old and new application versions can coexist during staged deployment where practical.
Risky changes
Take/confirm an appropriate recovery checkpoint before high-risk schema/data changes and test migration behavior outside production.
Execution
Apply migrations through a controlled deployment step or explicitly authorized migration job, not developer workstation scripts against production.
Failure handling
Define whether a failed release rolls application code back or rolls forward with a corrective migration; destructive down-migrations should not be assumed safe.
Audit
Retain migration/version and deployment history for operational diagnosis.

Area
Operational Direction

# 12. Independent Pre-Production Security & Architecture Validation
Before production launch, RetirementTrack should complete a focused independent review of the implemented security and operational controls. The reviewer should be qualified and independent from the developer or team responsible for implementing those controls. The objective is to verify that the actual production environment matches the approved architecture and Task 9 requirements, without turning the MVP into a burdensome enterprise audit or formal compliance certification.
Review area
What should be independently validated
Tenant isolation
Verify that one firm/client cannot access another firm’s identifiable data across APIs, database access paths and background workflows.
Identity & access
Review Clerk integration, application authorization, RBAC, MFA, advisor/client relationships, privileged access and least-privilege assignments.
Azure & environment configuration
Confirm production resources, environment separation and production access follow the approved architecture.
Secrets & credentials
Validate Key Vault, Managed Identity where supported, credential storage/rotation, pipeline secrets and absence of exposed production secrets.
Production-data controls
Confirm production client data is not routinely copied to lower environments or developer devices and that support/export access is controlled and auditable.
Logging, monitoring & audit
Confirm sensitive payloads are excluded from broad logs and that monitoring, alerts, audit evidence and operational visibility work as intended.
Backup & recovery
Review Azure SQL/Blob/Key Vault recovery configuration and evidence of restore testing against the approved recovery approach.
Deployment controls
Review CI/CD approvals, migration controls, deployment identities, rollback/roll-forward procedures and production change traceability.
Findings & closure
Document findings by severity. Material/high-risk findings should be remediated or formally accepted by RetirementTrack before production launch, with revalidation where appropriate.
This independent validation should be included as a pre-production implementation activity and budget item. It is intended as a practical second set of eyes on the implemented controls. Broader penetration testing, compliance certification or formal audit can be added later if client, insurer, regulatory or commercial requirements justify it.
# 13. Backup, Recovery & Business Continuity
Area
Recommended Approach
Azure SQL
Use Azure SQL automated backups and point-in-time restore capabilities; configure retention appropriate to confirmed production requirements.
Blob Storage
Use suitable redundancy plus soft delete/versioning/lifecycle features where they support recovery requirements.
Key Vault
Enable appropriate soft-delete/purge-protection and document recovery of critical secrets/certificates.
IaC / source
Git + Bicep provide reproducible application/infrastructure definitions but do not replace data backups.
Restore testing
Periodically test restoration into an isolated environment and document elapsed time, dependencies and issues.
RPO / RTO
Exact production Recovery Point Objective and Recovery Time Objective remain business confirmations and must be finalized before production launch.
# 14. Production Data Restrictions
Rule
Operational Requirement
Lower environments
Do not copy production client data into Dev/QA/Staging by default. Use synthetic or sanitized datasets.
Developer devices
Do not download production databases, client files or bulk exports to developer machines for routine troubleshooting.
Support access
Use authorized, least-privilege access and prefer metadata/status views over sensitive payload inspection.
Exports
Generate firm/client exports only through approved, auditable paths and according to confirmed portability/privacy policy.
Database access
Restrict direct production SQL access; use application/admin tooling where feasible and audit exceptional access.
Logs
Do not use logs as a secondary store for sensitive client information.
# 15. Incident & Support Approach
Stage
Recommended Practice
Detect
Monitoring/alerts, provider notifications or user reports identify an operational issue.
Triage
Establish severity, affected tenants/users, security/privacy implications and immediate owner.
Contain
Limit impact: disable failing workflow/integration, roll back deployment, revoke credential or isolate affected component as appropriate.
Recover
Restore service/data using documented release, backup or provider recovery procedures.
Communicate
Use agreed escalation and client/firm communication responsibilities; avoid speculative or premature incident statements.
Review
For material incidents, record timeline, cause, corrective actions and follow-up ownership.
Evidence
Preserve relevant deployment, audit, application and provider evidence consistent with privacy/retention policy.
Exact operational support hours, response expectations, escalation contacts and any service-level commitments remain business confirmations rather than assumptions in this Discovery document.

# 18. Developer / Vendor Onboarding & Offboarding
Phase
Required Actions
Onboarding
Create named identity; enforce MFA; grant only required repo/Azure/provider roles; document access owner and purpose; provide approved development/runbook documentation.
During engagement
Avoid shared credentials; use approved secrets/configuration paths; request temporary elevation only when necessary; keep work and deployment history in RetirementTrack-controlled systems.
Role change
Review and reduce access when responsibilities change.
Offboarding
Remove repository, Azure, Clerk, Temporal, provider, VPN/remote and other production access promptly; revoke tokens/keys; rotate shared/non-user credentials if exposure is possible.
Handoff
Transfer open work, deployment knowledge, runbooks and unresolved operational issues before engagement ends where practical.
Verification
Confirm RetirementTrack retains billing, account-owner and recovery access and that no vendor-only dependency remains.

# 21. Final Recommended Operational Boundary
Recommended first-build operational boundaryEstablish a professional but lightweight operating foundation: RetirementTrack owns the critical accounts and recovery paths; developers/vendors remain replaceable; environments and deployments are reproducible; production access is controlled and auditable; secrets are centrally managed; monitoring and recovery are documented; restore/deployment procedures are tested; and the implemented security controls receive an independent pre-production review. Avoid enterprise bureaucracy that does not improve MVP reliability, security or portability.
