RETIREMENTTRACK

Domain & Data Model

1. Purpose and Scope

Define the initial RetirementTrack domain model, data ownership boundaries and key relationships required to support the first credible MVP.

Task 4 outcome: a tenant-aware business model that clearly identifies the core entities, ownership, relationships, lifecycle, authorization boundaries and unresolved business decisions before detailed technical architecture is finalized.

2. High-Level Domain Structure

Platform → Firm/Tenant → Tenant Memberships & Configuration → Advisors / Clients → Assignments → Assessments / Planning Updates / Opportunities / Content / Reminders / Communications → Updated Client State / Advisor Exceptions

The primary security and ownership boundary is the Firm/Tenant. Platform-level data may be shared across tenants only where explicitly designed as common platform content or configuration. Client-specific records remain tenant-scoped even when they originate from common definitions such as an assessment template or educational resource.

PlatformPlatformUserRole, PlatformContent, common configurationOperate tenants and shared platform resources without routine unrestricted client-data access.
Firm / TenantFirmTenant, TenantConfiguration, TenantUserMembershipOwn firm-specific users, settings, branding, controls and client relationships.

EngagementAssessmentAssignment, AssessmentResult, PlanningUpdate, PlanningOpportunity, Reminder, CommunicationDrive recurring client activity and advisor attention.
Content / RelevanceContentItem, ContentTag, ContentAvailability, ClientContentStateSurface approved content based on known context and firm controls.
BenchmarkingBenchmarkDefinition, BenchmarkDataSet/Version, ClientBenchmarkResultProvide a bounded, explainable comparison when methodology is validated.
Governance / HistoryAuditEvent, ActivityHistory, configuration historySupport traceability, continuity, security and operational support.

3. Tenant / Firm Model

3.1 Recommended MVP Definition

For the initial model, one FirmTenant represents one independently administered RetirementTrack customer organization and is the top-level business, configuration and security boundary.

Tenant ownershipAll client/advisor/workflow data belongs to one tenant unless explicitly platform-global.Shared platform definitions must not create cross-tenant client visibility.

4. User and Role Model

Identity, tenant membership, role and client assignment should be modeled separately. This prevents the application from treating a user role as proof of tenant or client access.

EntityRecommended Responsibility
UserPlatform identity record: name, email/login identity, user status and authentication linkage.
TenantUserMembershipLinks a User to a FirmTenant and records membership status/effective dates.
UserRoleAssignmentAssigns one or more tenant-scoped roles to a membership.
PlatformRoleAssignmentStores platform-level operational roles separately from firm membership.
ClientProfileHolds client-specific profile/context separate from the authentication identity.
AdvisorProfileOptional advisor-specific professional/contact attributes used by RetirementTrack.

4.1 First-Build Roles

RoleCore AccessMust Not Assume
ClientOwn profile/experience; assigned activities; supported results/content/status.Access to other clients or administration.
AdvisorAuthorized/assigned clients; assignment/recommendation, review, approvals, follow-up/history.Automatic access to every client in the firm.
Firm AdministratorFirm users, branding, feature/communication/content controls, assignment governance.Unrestricted access to sensitive client data by default.
Platform AdministratorTenant/status/content/configuration and operational support.Routine unrestricted access to client financial/assessment data.

4.2 Multiple Roles and Multiple Firms

QuestionRecommended Data-Model PositionBusiness Confirmation Needed
Can one user have multiple roles?Yes at the data-model level. A membership may carry more than one role assignment.Confirm which combinations are permitted in MVP, e.g. Advisor + Firm Administrator.
Can one user belong to multiple firms?Support multiple TenantUserMembership records technically.Confirm whether MVP workflows permit multiple active memberships, especially for clients.
Can a Platform Administrator also belong to a firm?Technically possible, but platform authority should remain separately modeled.Confirm operational policy and support-access controls.

5. Advisor–Client Relationship

Advisor access should be based on an explicit tenant-scoped relationship, not merely on the Advisor role. The assignment record should support authorization, ownership, reassignment and history.

AreaRecommended MVP Model
Relationship entityAdvisorClientAssignment links Advisor membership/profile to a Client within the same FirmTenant.
Primary advisorAllow zero or one active PrimaryAdvisor assignment per client; use as default advisor identity and follow-up owner where applicable.
Secondary advisorsKeep the schema capable of additional assignments, but enable only if business need is confirmed.
ReassignmentEnd the prior assignment with EffectiveTo/Ended status and create a new assignment; do not overwrite history.
Historical assignmentsRetain prior assignments for audit, communication context and historical workflow attribution.
VisibilityAdvisor client access requires same tenant + active authorized assignment (or another explicitly approved permission path).
Firm Admin visibilityFirm Admin can manage relationships but should not automatically receive unrestricted sensitive client detail.
Open work transferDefine whether reassignment transfers open exceptions/follow-up items to the new advisor or preserves prior ownership.

6.1 Household Model

Household support is now part of the recommended MVP domain. The model should link spouses/partners without replacing each person’s individual identity, login, assessment history or permissions.

Entity / ConceptRecommended MVP Model
HouseholdTenant-scoped relationship container for a spouse/partner household. Hold shared household context only where the business meaning is genuinely shared.
HouseholdMemberLinks an individual ClientProfile to a Household with relationship type, effective dates and an optional primary/contact indicator.
Individual identityEach spouse/partner remains a separate User/ClientProfile with independent authentication, consent, assessment results and activity history.
Shared advisor relationshipHousehold members may share an advisor, but advisor authorization should still resolve to explicit client assignments unless a future household-wide rule is deliberately introduced.
Shared data boundaryUse household-level fields only for data naturally defined at household level, such as household income/net worth when required for benchmarking; avoid duplicating personal data.
MVP boundarySupport spouse/partner linking and shared context. Defer complex household hierarchies, trusts/entities and advanced shared-workflow behavior.

7. Assessments and Results

EntityPurpose / First-Build Boundary
AssessmentDefinitionDefines an approved assessment type; use a small fixed first-build inventory. Current working examples include a fuller client questionnaire and a condensed Investment & Risk Assessment.
AssessmentVersionPreserves question/scoring changes over time; completed assignments remain tied to their version.
AssessmentQuestion / OptionStructured questions and answer choices supported by the selected assessment.
AssessmentAssignmentLinks an assessment/version to a client, assigning advisor, due state and status.
AssessmentResponseStores answers for the assigned assessment.
AssessmentResultStores calculated score/category/output where methodology is defined.
AssessmentReviewCueCreates advisor attention when an approved result condition requires review; may map to the common exception/follow-up model.
Assessment history rule: never reinterpret a historical client result against a newer assessment version unless an explicit recalculation policy is defined.

8. Planning Update Model

Planning Update should be modeled as a recurring first-build workflow rather than a generic form. The model must support cadence, due state, client completion, comparison with prior state, defined change detection, advisor follow-up and updated client history.

Entity / ConceptRecommended First-Build Model
PlanningUpdateDefinitionFixed initial form/question set and version.
PlanningUpdateInstanceClient-specific scheduled/due occurrence with status, due date and completion date.
PlanningUpdateResponseClient responses for the instance.
Prior-state comparisonLinks relevant current values to prior completed state for defined change detection.
PlanningUpdateDetectedChangeStores each defined change with change type, prior/current value or references, severity/reason, advisor-attention flag and source Planning Update instance.
Follow-up linkOnly meaningful changes or explicit review conditions create an AdvisorException/FollowUp item. A completed Planning Update does not automatically create advisor work.
Client state updateCompletion/change outcomes update history and may alter future priorities, content or reminders.

11. Benchmarking Model

Benchmarking should be modeled as a small, credible first-build capability using curated reference data where the measure, source, cohort method, calculation and client-facing explanation are validated. Current working examples are median household income, median household net worth and median retirement savings by age; these are examples for evaluation, not automatically final production measures.

EntityPurpose / Boundary
BenchmarkDefinitionDefines the benchmark measure, unit, comparison method and client-facing explanation/caveat.
BenchmarkDataSourceRecords source provenance, maintainer, source type, publication/reference details and validation status.
BenchmarkDataVersionRepresents a versioned/effective snapshot of source data and methodology used for deterministic calculations.
BenchmarkReferenceValueStores curated reference values by benchmark definition, age/age band or other validated cohort dimension, percentile where applicable, effective year/version and source.
BenchmarkCohortDefines explainable cohort logic such as age or retirement stage where a separate cohort abstraction is useful.
ClientBenchmarkResultStores the client comparison result or reproducible calculation reference, including client input snapshot/reference, benchmark version and generated date.
BenchmarkVisibilityFirm enablement and advisor/client visibility according to permissions and MVP configuration.
Fallback stateIf required client inputs or validated benchmark data are unavailable, represent unavailable/not-calculable rather than fabricate a result.

12. Tenant Configuration and Permissions

12.1 Configuration Hierarchy

Platform capability → Firm/Tenant setting → Role / advisor-client authorization → Client-specific state / approved override

The MVP should keep this hierarchy small and predictable. Firm-disabled capabilities should not be silently re-enabled through a client override unless a specific exception is intentionally supported.

15.1 Working Business Guidance Confirmed During Discovery

AreaWorking Direction
Target firm modelDesign for established independent wealth-management and CPA/advisory firms with multiple professionals and several hundred to a few thousand client households.

17. Final Recommended Domain Boundary

Recommended domain core: Firm/Tenant + membership/roles + clients/advisors + explicit advisor-client assignments + assessment/result history + recurring Planning Updates + explainable priority/opportunity state + relevant content + reminders/communications + advisor exceptions + tenant configuration + bounded benchmarking + audit/history.
Include as First-Build DomainKeep Simple / Defer
FirmTenant, tenant configuration, user membership, built-in roles, Household/HouseholdMember and advisor-client assignmentsNo enterprise org hierarchy, complex household structures, brand tree or custom permission designer.
Fixed assessment definitions/versions, assignments, responses and resultsNo generalized assessment/form builder.
Fixed Planning Update workflow with prior-state comparison, explicit detected changes and follow-up linkageNo generalized workflow engine.
Rules-based priorities/opportunities, client state and content relevanceNo AI/ML recommendation engine or firm-authored rule builder.
Reminder/communication records, approval state and historyNo marketing automation/campaign platform.
Benchmark definition/source/version/reference-value entities sufficient for a small validated age/cohort comparisonNo sophisticated cohort analytics, dynamic peer benchmarking or broad readiness scoring.
Audit/history and tenant-scoped authorization metadataNo unnecessary duplication of every business event into a large event-sourcing platform.
