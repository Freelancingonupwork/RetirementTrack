RETIREMENTTRACK
Azure/.NET Technical Architecture
# 1.1 Architecture Goals & Principles
This architecture translates the product, workflow, domain, privacy and MVP-prioritization decisions from Discovery into a concrete Azure/.NET implementation blueprint. It is intentionally detailed enough for implementation planning while keeping the first build disciplined.
Operating model: RetirementTrack guides and engages -> the client learns and acts -> the platform records progress and follows up -> the advisor sees engagement, outstanding items and true exceptions -> professional help is brought in where it adds value.

# 1.6 Azure SQL & Data Architecture
Selected database: Azure SQL Database using a shared-database multi-tenant model. Every tenant-owned business record carries FirmTenantId/TenantId and is protected by layered tenant enforcement.
Area
Architecture Decision
Tenancy model
Shared database for MVP. FirmTenant is the top-level business/security boundary. Avoid database-per-tenant operational complexity unless future enterprise requirements justify it.
Core hierarchy
FirmTenant -> TenantUserMembership -> UserRoleAssignment / ClientProfile / AdvisorProfile -> Household / AdvisorClientAssignment -> workflow and engagement data.
Relational integrity
Tenant-aware foreign keys/composite uniqueness where relationships are tenant-specific. Prevent cross-tenant references at database level where practical.
Indexes
TenantId-leading indexes on high-volume access paths; additional indexes for advisor/client/status/due-date and activity queries.
Transactions
Use one transactional boundary per business use case where immediate consistency is required; enqueue background work only after state is committed.
Migrations
EF Core migrations generated in source control, reviewed, tested in lower environments and applied through controlled deployment pipeline.
Audit
Security/business audit records stored separately from operational logs; preserve actor, tenant, action, target, timestamp and reason/metadata.
Retention/deletion
Default offboarding assumption: when a firm leaves RetirementTrack, provide a 30-day post-termination transition/retention window for authorized firm export and, where business/legal policy permits, individual client or household portability. After 30 days, tenant/client data is scheduled for deletion, subject to contractual/legal/regulatory retention, legal hold, backup lifecycle, and other documented exceptions. The 30-day default is configurable policy and can change without architecture redesign. All export, retention and deletion actions are tenant-scoped and audited.
Backup/recovery
Azure SQL point-in-time restore baseline; formalize RPO/RTO before production launch and test restores periodically.

# 1.7 Multi-Tenancy & Data Isolation
Control Layer
Enforcement
Request tenant context
Resolved server-side from the authenticated RetirementTrack membership. Browser-supplied TenantId is never trusted as proof of authorization.
EF Core read isolation
Global query filters on all ITenantEntity types automatically apply the active TenantId.
EF Core write isolation
SaveChanges interceptor assigns TenantId for inserts, blocks TenantId mutation and rejects cross-tenant update/delete attempts.
Resource authorization
ASP.NET Core authorization handlers verify same tenant plus client/household/advisor relationship and role.
Database constraints
Tenant-aware foreign keys/composite keys/unique constraints prevent invalid cross-tenant relationships.
Database defense
Use Azure SQL Row-Level Security for the most sensitive tenant tables where practical, with server-established session context. RLS is defense in depth only and does not replace application authorization, EF Core tenant filters, or relationship-level access checks.
Background jobs
Every job carries TenantId explicitly and creates a tenant context before loading data.
Cache/files
TenantId is included in tenant-owned cache keys and storage paths; storage path alone is never considered authorization.
Query bypass
IgnoreQueryFilters/raw SQL limited to reviewed privileged infrastructure code paths and audited.
# 1.8 Identity & Authorization
Recommended MVP identity provider: Clerk Pro. Clerk Pro costs $20/month when billed annually, or $25/month when billed monthly. It provides 50,000 Monthly Retained Users (MRUs); usage above 50,000 MRUs is charged at $0.02 per additional MRU per month. Clerk authenticates users; RetirementTrackauthorizes access. FirmTenant membership, roles, household relationships, and advisor-client assignments remain application data.
## 1.8.1 Invitation / Activation Flow
Step
Flow
1. Invitation
Firm/Admin creates or invites the intended client/advisor. RetirementTrack creates User + TenantMembership + relationship context and a secure invitation state.
2. Activation link
User follows a RetirementTrack activation link. Invitation validity, tenant status and intended account are verified.
3. Clerk registration/sign-in
Clerk handles credential creation, verification, password reset, MFA and session/token issuance.
4. Identity linkage
Clerk user identifier is linked to the pre-existing RetirementTrack UserExternalIdentity record. Email is bootstrap/contact data, not the permanent authorization key.
5. Business onboarding
RetirementTrack records consent/household-sharing acknowledgment, minimum profile, household/advisor relationship and initial personalization.
6. Protected access
API validates Clerk token, resolves RetirementTrack user/membership/role/relationships and applies resource authorization.
## 1.8.2 MFA and Session Direction
User Type
Recommended Policy
Platform Administrator
MFA mandatory. Shorter privileged session and audited support actions.
Firm Administrator
MFA mandatory.
Advisor
MFA mandatory because advisor access includes sensitive client planning information.
Client
MFA mandatory for production because RetirementTrack may contain household, planning, assessment and high-level financial information. # 1.11 Background Processing
Recommendation: use Temporal Cloud with an Azure-hosted .NET Temporal Worker for the MVP. Keep workflow/activity execution logically separate from the interactive API process. Temporal Cloud provides the managed durable orchestration service for schedules, timers, retries and long-running workflows, while RetirementTrack owns and deploys the Worker code in Azure. This avoids operating and maintaining a self-hosted Temporal cluster, persistence layer, upgrades, backups and high-availability infrastructure. Pricing is consumption-based. As of September 2026, Temporal's AWS Marketplace pay-as-you-go offering lists a $100/month plan fee plus $50 per million Actions, with storage and any applicable support/plan costs varying by usage and plan. Validate final commercial terms and projected Actions/storage immediately before implementation.
Job Type
Examples
Execution Rule
Reminder jobs
Planning Update reminder, assessment reminder, milestone reminder.
Tenant-scoped, idempotent, cancelled/stopped when the related activity completes.
Milestone evaluation
Age 64.5/65 Medicare, Social Security, RMD preparation, retirement timing.
Evaluate defined rules tenant-by-tenant and create/update client priority state.
Communication delivery
Invitation, reminder, approved message, notification.
Persist communication first, send via provider, record retry/delivery/failure.
Planning Update scheduling
Create due instances from cadence rules.
Do not create advisor work unless later change rules require it.
Maintenance
Data lifecycle processing, cleanup, export jobs, stale invitation expiry.
Audited where security/data lifecycle is involved.
Future sync
CRM/calendar/provider synchronization.
Introduce Service Bus/event-driven workers only when volume/integration complexity warrants it.
Temporal workflow payloads should carry stable IDs and TenantId, not large sensitive data payloads. Temporal Cloud provides durable workflow execution, timers and retries for reminders, communications and other asynchronous processes. Activities must remain idempotent and establish tenant context before loading or changing tenant-owned data.

# 1.14 Security & Privacy
Area
Architecture Requirement
Encryption in transit
HTTPS/TLS only across browser, API, providers and Azure services.
Encryption at rest
Azure SQL, Blob Storage and backups use platform encryption; consider field-level encryption only for specific risks that justify it.
Least privilege
Azure RBAC, managed identities, scoped support roles and no shared production credentials.
Household privacy
Authorized household participants share household information by default after acknowledgment. Individual/private classification remains available where needed.
Advisor visibility
Dashboards show useful engagement/status/exception information without unnecessarily exposing detailed sensitive financial values.
Platform support
No routine unrestricted client-detail access. Any privileged support access should be justified, controlled and audited.
Data minimization
Collect only high-level planning/benchmarking/personalization data required by approved workflows.
No cross-firm exposure
Identifiable tenant/client data from one firm is never exposed to another firm.
Future analytics
Proprietary benchmarks may later use appropriately aggregated/de-identified platform data behind separate privacy/legal controls; not live cross-tenant identifiable queries.
Firm/client portability
Architecture supports firm-level export, tenant-scoped Blob packaging, individual client/household portability where approved by business/legal policy, auditable retention/deletion workflows, and a default 30-day post-termination transition window. After the window, data is scheduled for deletion subject to documented legal/regulatory, legal-hold and backup-lifecycle exceptions. Portability never permits cross-firm exposure by default.
## 1.14.1 Data Classification
Use a simple data-classification model to drive logging, support access, export handling, household sharing and privacy controls: Public (approved public content), Internal (non-client operational/configuration data), Tenant Confidential (firm-specific settings and operational data), Client Sensitive (planning, assessment, financial and workflow data), and Individual Private (client data intentionally excluded from shared household visibility). Classification should guide least-privilege access and prevent sensitive values from entering logs or broad support views.
