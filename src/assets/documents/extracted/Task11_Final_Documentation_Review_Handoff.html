Task 11 - Final Documentation, Review & Handoff

RetirementTrack MVP Discovery

1. Discovery Summary

RetirementTrack is a white-label B2B SaaS platform for retirement-planning and advisory firms. The MVP is designed to create an ongoing retirement relationship rather than a one-time assessment or collection of forms. It combines client self-service, recurring planning activity, educational content, reminders, benchmarking, and advisor visibility while intentionally minimizing routine advisor workload.

Operating Model: RetirementTrack guides and engages -> the client learns and acts -> the platform records progress and follows up -> the advisor sees engagement and true exceptions -> professional help is brought in where it adds value.
Product DimensionMVP Direction
Client experienceSelf-directed, personalized and recurring. A client should quickly understand where they are, what deserves attention, and what to do next.
Advisor experienceHigh visibility with low routine workload. Routine completion and reminders are platform-managed; advisors focus on client requests and defined professional-attention conditions.
Retirement lifecycleBefore retirement: understand both planning progress and whether financial resources reasonably support the retirement being planned. During retirement: continue planning engagement while monitoring whether the retirement remains financially sustainable. Retirement is a stage transition, not an endpoint.
EducationA growing library is a core engagement mechanism, available through direct browsing and contextual surfacing.
Retirement Planning ProgressShow visible coverage of the client's applicable retirement-planning journey: addressed areas, accomplishments, upcoming milestones and outstanding planning areas. This dimension measures planning progress only and must not imply financial adequacy or sustainability.
MVP boundaryNo account aggregation, trading, portfolio management, generalized form/workflow builders, broad analytics engine or individualized automated financial/investment/tax/legal advice.
Financial Preparedness / SustainabilityTreat financial preparedness before retirement and ongoing financial sustainability during retirement as a separate product dimension. Support multiple independent, versioned financial measures/tests rather than one universal readiness score. Exact calculations, assumptions, inputs and status thresholds remain product/domain work to be defined.

2.1 Core Client Workflow

Invitation -> Account Activation -> MFA -> Consent / Household Sharing Acknowledgement -> Minimum Profile -> Household / Advisor Context -> First Personalized Dashboard -> Planning Update / Assessment / Education -> Retirement Planning Progress & Milestones -> Reminders -> Advisor Contact or Exception when needed -> Returning Dashboard with updated state.

2.2 Planning Update Workflow

Periodic offer / approved event trigger / optional advisor request -> client opens -> asks whether anything meaningful changed -> No Change: confirm quickly, record result, refresh engagement state and stop applicable reminder sequence -> Yes: branch only into relevant sections, show prior values where useful, allow save/resume, submit versioned responses -> compare prior/current -> apply explicit material-change rules -> update progress/priorities/content -> create AdvisorException only for a configured material condition or explicit client request -> preserve history/version.

2.3 Assessment Workflow

Approved assessment is enabled by the firm and becomes available / is recommended / assigned -> client starts -> save/resume -> submit -> deterministic scoring/result logic for that published assessment version -> client-friendly result with caveats and relevant education -> preserve original version/history -> optional prior/current comparison where meaningful -> AdvisorException only for explicitly configured material result/threshold change or client request -> retake only according to that assessment cadence, advisor request, or appropriate material client change.

2.4 Advisor Workflow

Advisor signs in -> sees assigned-client summaries -> reviews Engagement & Accomplishments / Outstanding Client Items / Advisor Attention separately -> searches/filters households -> opens authorized client detail -> reviews relevant Planning Update/assessment changes -> acknowledges or resolves true exceptions -> responds to client-requested contact -> does not receive routine completion as a task.

2.5 Post-Retirement Engagement Workflow

Age/calendar/retirement-stage/client-context trigger -> evaluate approved deterministic rule -> surface education, priority, reminder or review prompt -> optionally encourage advisor contact -> create AdvisorException only if the approved rule warrants professional attention. Examples include RMD preparation/completion, withdrawal/draw-rate review, Medicare/IRMAA considerations, QCD opportunities, beneficiary/estate/insurance reviews, and income/spending changes. These engagement prompts remain distinct from any approved Financial Preparedness / Ongoing Financial Sustainability calculation, which is presented as a separate financial dimension.

2.6 Detailed Module Implementation Specifications

The following module specifications consolidate the final Discovery direction and latest product decisions into implementation-ready behavior. They define what another delivery team should build while preserving the approved Azure/.NET architecture and MVP boundaries.

2.6.1 Assessments

Assessments are a RetirementTrack-owned engagement capability. The MVP must support a defined, versioned catalog maintained by the platform; each firm controls which approved assessments are available to its clients. The catalog should remain extensible without introducing a generalized assessment/form builder.

Implementation AreaRequired MVP Behavior / Developer Direction
Ownership & availabilityPlatform Admin manages approved AssessmentDefinition/AssessmentVersion records. Firm Admin enables/disables approved assessments for that tenant. An enabled assessment may be surfaced by deterministic eligibility rules or recommended/assigned by an authorized advisor.
Scoring modelEach assessment owns its own scoring/output contract: numeric score, category/band, flags, educational result or no-score completion. Persist the exact scoring/version reference with the result. Do not aggregate assessment outputs into one RetirementTrack financial-readiness score.
Lifecycle & historySupport available/recommended/assigned, started/in-progress, submitted, scored/completed and optional reviewed context as appropriate. Longer assessments support save/resume. Every completion remains tied to the exact published version used at that time; do not silently recalculate historical results after a version change.
Repeat / retake rulesRetakes are allowed only according to the cadence defined for that assessment, by authorized advisor request, or after an appropriate material client change. Avoid unrestricted repeated submissions.
Advisor impactNormal completion is an Engagement/Accomplishment. Incomplete/due items remain client-facing/outstanding where applicable. Create AdvisorException only for assessment-specific configured material results/threshold changes or an explicit client request for help.
API / service responsibilityExpose tenant-authorized APIs for firm-enabled catalog, start/resume, response save, submit, result/history and advisor-authorized context. Scoring and threshold evaluation execute server-side against immutable/versioned definitions; UI must not be the source of scoring or authorization truth.
Failure / fallbackIf scoring fails after submission, preserve submitted responses and submission version, show a processing/retry state, retry safely where appropriate, and alert operations if persistent. Never discard the client submission or fabricate a result.
Acceptance criteriaA firm can enable an approved assessment; an authorized client can complete it; the same inputs produce the deterministic versioned result; history remains reproducible after a newer version is published; cross-tenant access is blocked; configured material thresholds create an advisor exception and normal completions do not.
Out of scopeFirm-authored assessment builder, arbitrary rule scripting, unrestricted retakes, cross-assessment readiness engine, AI scoring/recommendations and automated individualized financial/investment advice.

2.6.2 Planning Updates

Planning Updates are a recurring engagement mechanism for detecting meaningful client changes with minimal friction. They are not a mandatory annual questionnaire by default and should not routinely depend on an advisor starting the process.

Implementation AreaRequired MVP Behavior / Developer Direction
Trigger modelThe platform periodically offers a change-check based on approved cadence/rules; appropriate life-stage/context events may also prompt an update. An advisor may request an update when useful, but advisor initiation is optional rather than the normal mechanism.
Fast No Change pathThe first interaction should ask whether anything meaningful has changed. If the client selects No Change, record the confirmation/version/source/time, complete that offered interaction quickly, update engagement/progress state and stop any reminders associated with that offer.
Yes Change branchingIf the client reports a change, route only to relevant sections/topics instead of forcing the entire questionnaire. Show prior known values where useful, permit safe save/resume for branched sections, validate server-side and persist the submitted version.
Comparison & materialityCompare approved fields/topics to the relevant prior completed state and create explicit PlanningUpdateDetectedChange records. Separate informational/relevant changes from configured material conditions. A change may update personalization/priorities/content without creating advisor work.
Advisor impactCompletion/no-change is visible as engagement. Create AdvisorException only when an explicitly configured material rule is met or the client asks for advisor help. Do not create routine advisor tasks merely because an update was offered or completed.
API / service responsibilityProvide APIs for current offer/status, prior-value context, section responses, save/resume, submit/no-change confirmation, history and authorized advisor summary. Business services own trigger source, comparison, versioning, materiality and exception creation; Temporal owns durable timing/reminder behavior.
Failure / fallbackIf comparison/materiality evaluation fails after a valid submission, preserve the completed update, mark evaluation pending/retryable, retry durably and avoid duplicate exceptions. The client should not need to resubmit because a downstream evaluation failed.
Acceptance criteriaNo Change can be completed with minimal steps; Yes branches only to relevant sections; history/version is preserved; prior/current comparison is reproducible; reminders stop after completion; ordinary changes update the client experience without advisor work; only configured material conditions or client requests create exceptions.
Out of scopeMandatory full annual questionnaire by default, generic workflow/form designer, advisor-required initiation, arbitrary scripting and automatic individualized financial/tax/legal recommendations.

2.6.3 Client & Household Structure

The MVP should support a household-oriented retirement experience while preserving individual identity, consent and bounded privacy. Keep the model simple enough for implementation and user comprehension.

Implementation AreaRequired MVP Behavior / Developer Direction
Identity modelEach spouse/partner is a separate authenticated User with their own identity, contact information, acknowledgements and activity attribution. Household membership links authorized individuals without merging identities.
Minimum profileCollect only information necessary to establish the first personalized experience and approved workflows, such as name, DOB/age, retirement status/timing, household relationship, advisor context and limited high-level planning information. Collect additional financial context only when a specific approved workflow requires it.
Sharing modelAfter explicit household-sharing acknowledgement, household-level planning information is generally shared among authorized household participants. Support a bounded Shared vs Individual/Private classification for selected information. Do not implement field-by-field spouse permission matrices in MVP.
Advisor relationshipPresent one Primary Advisor in the client experience. The underlying AdvisorClientAssignment model may support additional advisor relationships/types and effective dates so the architecture does not require redesign later.
Authorization boundaryEvery client/household API must verify authenticated tenant membership plus household membership or active advisor assignment. Tenant role alone is insufficient for access. Individual/Private data must be excluded from household responses and advisor views unless the requesting user is explicitly authorized.
Data minimizationDo not collect account credentials, account numbers, transactions, individual holdings or statement-vault data. High-level account type/ownership, approximate/current balance, income, savings or net-worth context may be stored only when needed by an approved workflow/benchmark.
Acceptance criteriaTwo spouses can have separate logins linked to one household; shared information is available only after acknowledgement; Individual/Private information does not leak through household/client/advisor APIs; one Primary Advisor is shown; an advisor without an active assignment cannot access the household.
Out of scopeComplex per-field spouse permissions, unrelated-person household structures unless later approved, account aggregation, brokerage credential storage and unrestricted Firm Admin access to sensitive client information.

2.6.4 Educational Content

Education is a core recurring-engagement mechanism. RetirementTrack curates the master library; firms select which approved content is available. The MVP should support direct discovery plus deterministic contextual surfacing without becoming a full content-management product.

Implementation AreaRequired MVP Behavior / Developer Direction
Content inventorySupport approved videos, guides/brochures, one-pagers, infographics, articles/brief insights, factoids/Did You Know items, checklists and benchmark explanations. Store type, title/summary, publish/availability metadata and controlled content references/assets.
TaxonomyUse controlled tags for topic, life stage, age/milestone, workflow relevance and content type. Keep ContentItem-to-ContentTag many-to-many. Avoid uncontrolled free-form tagging that would make personalization inconsistent.
Firm availabilityPlatform Admin owns the master RetirementTrack library. Firm Admin may enable/disable approved content/categories for its tenant. MVP does not require firms to author/upload/manage a separate content library.
Contextual surfacingUse deterministic rules based on age, retirement stage, milestones, Planning Update changes, assessment results, household context, prior completion and firm availability. Surface a bounded number of relevant resources; do not use AI ranking/recommendation in MVP.
Engagement trackingTrack meaningful states only: surfaced where useful, opened/viewed, downloaded, content-specific completed state and selectively dismissed/not interested. Do not collect exhaustive clickstream behavior. Advisor views should show meaningful engagement summaries rather than every page interaction.
Completion semanticsUse content-specific completion rules: e.g., watched threshold for a video when configured, explicit completion for checklist, opened/viewed for article/guide unless richer tracking is justified. Historical engagement should remain understandable if content is later unpublished.
Failure / fallbackIf content is unpublished/removed, do not break historical engagement records; show unavailable/replacement behavior where appropriate. If a contextual rule references unavailable content, omit it and continue with other eligible items rather than failing the dashboard.
Acceptance criteriaClients can browse/search/filter enabled content; firms can select availability from the platform catalog; contextual rules never surface disabled content; meaningful engagement is persisted; historical activity remains readable after content changes; no cross-tenant exposure occurs.

2.6.5 Benchmarking

Benchmarking is an optional educational comparison capability using validated external/reference data. The exact measures are a product decision and must not be hard-coded around income, net worth or retirement savings simply because those were earlier examples.

Implementation AreaRequired MVP Behavior / Developer Direction
Definition modelImplement BenchmarkDefinition, BenchmarkDataSource, BenchmarkDataVersion, optional Cohort/reference values, ClientBenchmarkResult and visibility/availability metadata. The model must support different future measures without schema redesign.
Activation criteriaDo not activate a benchmark until the source, methodology, cohort rules, effective period, legal/usage rights and client-facing explanation/caveat are approved. Exact initial benchmark measures remain TBD by product/domain review.
CalculationUse deterministic server-side calculation against the active validated data version and only the minimum client/household inputs required for that measure. Persist enough source/version/method references to reproduce the historical result.
PresentationShow a neutral comparison with source/year or effective period, methodology/caveat and educational explanation. Avoid judgmental good/bad labels and avoid implying financial readiness or professional advice.
History & updatesPreserve historical results with the dataset/methodology that applied when generated. A newly validated data version may generate a new current comparison; do not silently rewrite old results.
Unavailable stateIf required client inputs, a validated source/version or cohort value are missing, return unavailable/not-calculable with a clear reason rather than fabricating or extrapolating a result.
Tenant / privacy boundaryFirm enablement and client/advisor visibility remain tenant-scoped. Do not query or expose identifiable data from other RetirementTrack firms/clients to build MVP comparisons.
Acceptance criteriaA product-approved benchmark can be loaded/versioned/activated; calculation is reproducible; historical results survive source updates; invalid/inactive source versions cannot produce new results; missing inputs show unavailable; presentation includes provenance/caveat.

2.6.6 Client Priorities

Implementation AreaRequired MVP Behavior / Developer Direction

TraceabilityEvery surfaced priority should carry enough internal metadata to explain which rule/source produced it and why. Do not expose sensitive underlying values on broad screens when a concise reason is sufficient.
Acceptance criteriaThe same client state/rule version yields the same bounded priority set; completing/dismissing an eligible item updates subsequent results; disabled content/features cannot generate priorities; conflicting rules follow explicit precedence/configuration and are traceable.
Out of scopeInfinite task feed, AI-generated priorities, opaque ranking, generalized rules builder and advisor task creation for every client interaction.

2.6.7 Reminders & Milestones

Reminders should support useful recurring engagement, not create recurring chores. Temporal Cloud should provide durable timers/retries while business rules control what is worth surfacing and when.

Implementation AreaRequired MVP Behavior / Developer Direction

Workflow executionTemporal workflows/activities should carry TenantId plus stable business identifiers, load authoritative data at execution time, schedule due/next times, retry idempotently and support cancellation/stop conditions. Avoid carrying unnecessary sensitive payloads inside workflow state.
Bounded sequencesWhere repeated reminders are appropriate, use a bounded sequence with frequency caps. Prevent duplicate active reminders for the same source and avoid too many simultaneous client prompts.
Stop / dismiss behaviorCompletion/acknowledgement stops applicable routine reminders. Informational/educational items may be snoozed or dismissed when allowed. Planning Update prompts follow the lightweight offer model rather than being universally mandatory; any hard-required state must be explicitly configured.

Failure / fallbackDelivery/workflow failures use bounded retries and record operational status. Idempotency must prevent duplicate communication or duplicate advisor exceptions. Persistent failures should be observable through monitoring without losing the underlying client state.
Acceptance criteriaTimers survive worker restarts; completion cancels remaining reminder steps; duplicate triggers do not create duplicate active reminders; tenant context is preserved; informational snooze/dismiss works where configured; routine reminders do not create advisor tasks.
Out of scopeBroad marketing automation, high-frequency campaign sequencing, mandatory completion of every reminder, unmanaged cron jobs and advisor-created custom workflow designer.

Failure / fallbackOn SendGrid delivery failure, bounce, block or deferred event, use bounded retry where appropriate, record delivery state and surface operational alerts when significant. Process SendGrid event/webhook callbacks idempotently and do not duplicate sends on retries. In-app state remains independently available when email delivery fails where the workflow supports it.
